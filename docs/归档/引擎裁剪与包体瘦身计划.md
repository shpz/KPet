# 引擎裁剪与包体瘦身计划（UE 5.8 / KimiPet）

> 本计划由 10 路并行调研汇总而成，所有关键结论均经过三类渠道交叉验证：
> ① 本机 UE 5.8.1 引擎源码/产物实测（`C:/Program Files/Epic Games/UE_5.8`、`Pet/Saved/StagedBuilds`、`dist-plugin`）；
> ② Epic 官方文档与 API 文档（5.8 版）；③ Epic 官方论坛 / 社区实测文章。
> 每条结论的验证状态见文末"不确定项"，未找到可靠来源的说法均已标注。

## 一、基线：1.2G 产物实测拆解

`dist-plugin/kimi-pet/`（2026-08-01 构建，Development 配置）：

| 构成 | 体积 | 性质 |
|---|---|---|
| `Pet/Binaries/Win64/Pet.pdb` | 348M | 调试符号，不应分发 |
| `Pet/Binaries/Win64/Pet.exe` | 317M | Development 配置（Shipping 实测仅 161M） |
| `Pet/Content/Paks/Pet-Windows.ucas` | 229M | 已压缩（Oodle Kraken L4；08-10 构建日志口径 280M→228M）。内含：Shader 约 115M（50%）、NNEDenoiser 降噪模型约 98M、其余引擎内容约 13M；项目自身内容不足 1M |
| `bin/kimi-petd.exe` + `kimi-pet-bridge.exe` | 94M × 2 | Bun `--compile` 产物，各自内嵌完整 Bun 运行时（业务 JS 仅 143KB） |
| Vulkan 调试层 14 个文件（7 DLL + 7 JSON，khronos_validation 18.6M 等） | ≈40M | 纯调试组件，仅 Development 配置会暂存 |
| `DML/x64/DirectML.dll` + NNE 插件 `onnxruntime.dll` | 18M + 17M | NNERuntimeORT 链入，项目未使用神经网络推理 |
| `d3d12SDKLayers.dll` / `D3D12Core.dll` | 4.7M / 4.6M | D3D12 调试层（可删）/ Agility SDK 运行时（默认 D3D12 RHI 下必留） |
| NVIDIA NVaftermath | 5.5M | GPU 崩溃转储组件，Shipping 也会暂存 |
| `Engine/Content/SlateDebug/Fonts/LastResort.ttf` | 5.2M | 打包版不读取的死文件 |
| `Pet-Windows.pak` + `global.ucas` | 11M + 3.1M | 松散文件（ini/ufont 等），正常 |

> 注：体积均为 MiB 口径（`du` 四舍五入）。另有未列零散 ThirdParty 组件约 7M（MsQuic 2.5M、DbgHelp 2.2M、Vorbis/Ogg 1.8M、XAudio2_9 0.84M、tbb 0.45M 等），量级小，不影响结论。

两个关键事实：
- 项目 `Pet/Content` 源码仅 4.8M，**包体与项目资产无关，全部是引擎侧内容**。
- 引擎是 launcher 安装版（存在 `Engine/Build/InstalledBuild.txt`），**不能重编引擎模块**；所有"引擎裁剪"只能走项目层配置（.uproject / ini / 打包参数），这不构成障碍。

## 二、总体目标与阶段划分

**预计：1.2G → 阶段一~四后约 390~400M；阶段五 P1（合并）后约 300M，P2（Go 重写转发器）后磁盘仍约 300M**。阶段一~四确定性收益合计约 800M。

| 阶段 | 内容 | 预计收益 | 风险 |
|---|---|---|---|
| 一 | 打包链路统一为 Shipping + `-nodebuginfo` | **≈550M**（pdb 348M + exe 156M + Vulkan 层 40M + SlateDebug 5.2M） | 低，收益全部有本机实测 |
| 二 | 禁用 NNE 系插件 + MCP 限定 Editor | **≈133M**（onnxruntime 17M + DirectML 18M + NNEDenoiser 内容 98M，均实测） | 低 |
| 三 | 关闭桌面宠物用不到的渲染特性 + Shader 格式收敛 | **≈105~115M**（阶段二后 ucas 约 131M → 约 15~25M；与阶段二收益不重叠） | 中，需视觉回归 |
| 四 | 压缩配置固化 + 零散 DLL 决策 | ≈10M（SDKLayers 4.7M + NVaftermath 5.5M；Leviathan 可选再省 1~3M） | 低 |
| 五 | 桥接程序合并/重写 | P1 合并省 **94M**；P2 relay Go 化省约 92M，但与 P1 **不叠加**（终态均为 daemon 94M + relay ≈ 96M，P2 收益在冷启动） | 中 |

分档合计校验：1195 − 550 − 133 − 110 − 10 ≈ 392M（阶段一~四）；P1 后 − 94 ≈ 298M；P2 后 392 − 92 ≈ 300M（与 P1 基本持平，见第七节）。

每个阶段独立打包、独立量化、独立提交，方法见第七节。

## 三、阶段一：打包链路统一（收益最大，先做）

### 现状问题
- 根 `package.json` 引用的 `scripts/package.ts` **已被删除**（git 提交 5426adc），当前无打包脚本；dist 是 Development 产物且把 pdb 拷入，与 `Saved/StagedBuilds` 的 Shipping 暂存是两套不一致的链路。
- Shipping 与 Development 的机制差异（本机 rsp 对比 + 引擎源码核实）：Shipping 启用 `/OPT:REF /OPT:ICF`（`VCToolChain.cs`，仅 Test/Shipping 默认开）、剥离日志/控制台/stat/check（`Build.h`），exe 317M→161M；且**仅 Development 会暂存** 7 个 Vulkan 调试层 DLL（`DeploymentContext.cs:996`）与 WinPixEventRuntime（PIX `Build.cs` 依赖链，同为非 Shipping 限定）。

### 操作
1. 恢复/重建 `scripts/package.ts` 作为唯一打包入口，改为：
   - `-clientconfig=Shipping`（原为 Development）；
   - 追加 **`-nodebuginfo`**（UAT 官方参数，"do not copy debug files to the stage"）；
   - 组装 `cpSync` 后兜底删除 `renderer/` 下全部 `*.pdb`。
2. pdb 不随包分发，本地归档或接 BuildGraph `SymStore`（符号服务器），供崩溃分析用。
3. `DefaultGame.ini` 追加持久化配置（字段名经 `ProjectPackagingSettings.h` 逐行核实）：
   ```ini
   [/Script/UnrealEd.ProjectPackagingSettings]
   IncludeDebugFiles=False
   bSkipEditorContent=True
   bSkipMovies=True
   +CulturesToStage=zh-Hans
   +CulturesToStage=en
   +DirectoriesToNeverCook=(Path="/Game/Developers")
   ```
   - `IncludeDebugFiles`：仅编辑器内 Turnkey/Project Launcher 打包路径消费，对 RunUAT 命令行打包**不生效**；UAT 链路去 pdb 只靠操作 1 的 `-nodebuginfo`。写它只为编辑器路径一致性。
   - `bSkipEditorContent`：cook 时跳过 `/Engine/Editor*`、`/Engine/VREditor` 内容（本包约 110 条，<10M）。官方注释警告"若内容被使用会导致缺失"，改后需完整回归。
   - `CulturesToStage`：收窄 ICU 本地化数据。当前产物中本无 ICU 数据，收益≈0，配置仅作防回归。
   - 注意 `DirectoriesToNeverStage` 是网传误名，UE 5.8 中**不存在**该字段。
4. 验收：`tools/verify-pet-operations.ps1` 的 Shipping 路径（已适配无日志断言）+ 手动验证 ESC/点击关闭、管道 `close_pet`。

### 代价（已确认可接受）
- Shipping 下**无任何日志**（安装版引擎无法开启 Shipping 日志，官方 KB 明确需源码引擎才行）→ 线上排障依赖 Node 守护进程日志。
- 无控制台/stat/check；需自备退出路径（项目已有）。

## 四、阶段二：插件裁剪

### 4.1 禁用 NNE 降噪链（本阶段大头）
`NNEDenoiser`（PathTracing 神经降噪，`EnabledByDefault: true`）→ 依赖 `NNERuntimeORT` → 链入 `onnxruntime.dll` 17M + `DirectML.dll` 18M，且 OIDN 模型资产（约 100M）被 cook 进 ucas。项目运行时不用 PathTracing，Pet 源码对 NNE 零引用（已 grep 确认）。

`Pet/Pet.uproject` 的 `Plugins` 追加：
```json
{ "Name": "NNEDenoiser", "Enabled": false },
{ "Name": "NNERuntimeORT", "Enabled": false },
{ "Name": "NFORDenoise", "Enabled": false }
```
依据：`PluginManager.cpp` 中项目显式配置优先于 `EnabledByDefault`；`NFORDenoise`（5.8 新增的时空间降噪）同样默认启用且在包内。禁用后 PathTracing 失去 AI 降噪（阶段三将直接关闭 PathTracing，彻底无影响）。

### 4.2 MCP 插件限定编辑器
`ModelContextProtocol` 含 Runtime 模块，实测符号进了 Shipping exe。改法：
```json
{ "Name": "ModelContextProtocol", "Enabled": true, "TargetAllowList": [ "Editor" ] }
```
`AllToolsets`、`MCPClientToolset`（`EditorOnly` 字段）与 `ModelingToolsEditorMode`（模块 `Type: Editor`）均为编辑器限定且不进包，**保持现状不动**（改动零收益且会断编辑器内 AI 工具链）。

### 4.3 不建议做的事
- `DisableEnginePluginsByDefault: true`：会关掉所有默认启用的引擎插件（含 MetaHumanSDK 等），影响面大，收益相对小，非必要不做。
- 用 `DirectoriesToNeverCook` 排除 ControlRig/Interchange 等引擎插件内容：被运行时引用，强排除易破坏功能，收益仅几 M。

## 五、阶段三：渲染特性与 Shader 收敛

ucas 中 Shader 121M 里 99.9% 是**引擎内容材质的 shader 排列**（项目自有材质 shader 仅 85KB），排列数量由特性开关决定。对 2D 桌面宠物（单模型小场景、UI 为主），以下全部建议关闭（字段名经 `RendererSettings.h` 5.8 源码核对，官方文档均明示可减少 shader 数量/排列）：

`Pet/Config/DefaultEngine.ini` 的 `[/Script/Engine.RendererSettings]` 段：
```ini
r.PathTracing=False                  ; 官方："不用的项目应关闭以减少 shader 编译"
r.RayTracing=False
r.Lumen.HardwareRayTracing=False
r.RayTracing.RayTracingProxies.ProjectEnabled=False
r.DynamicGlobalIlluminationMethod=0
r.ReflectionMethod=0
r.Nanite.ProjectEnabled=False        ; CVar 帮助文本："关闭可减少 shader 数量"
r.VirtualTextures=False
r.MeshPaintVirtualTexture.Support=False
r.DBuffer=False
r.GenerateMeshDistanceFields=False   ; 官方 ToolTip："会增加静态网格磁盘大小"
r.Substrate=False                    ; 5.8 老项目默认关，需 opt-in
r.SupportStationarySkylight=False
r.SupportLowQualityLightmaps=False
r.SupportPointLightWholeSceneShadows=False
r.SupportSkyAtmosphere=False
r.SupportLocalFogVolumes=False
```
同时删除连带的 `r.Substrate.Project*`、`r.VT.*`、`r.vt.rvt.*`、`r.MeshPaintVirtualTexture.*`、`r.DistanceFields.*` 行。另在 `[ConsoleVariables]` 段加 `r.Lumen.Supported=0`（它是纯 CVar 而非 `RendererSettings` 的 UPROPERTY，编辑器设置 UI 不管理，按惯例放 `[ConsoleVariables]` 段；官方描述"避免编译 shader 与加载开销"；UE 5.6+ cook 会自动剥离禁用特性的 shader 排列）。

关闭后光照从 Lumen 退化为无 GI + 反射捕获，需检查 `L_Main` 光照观感；Substrate 材质会变黑（项目 30 个资产均无 Substrate 节点，改前在编辑器确认一遍）。

### Shader 格式决策（二选一，与上面联动）

本项目实测（08-01 构建的 `Pet/Saved/Cooked/Windows` + 打包日志；此后构建已覆盖，数值为该构建口径）：SM6 库 162M 未压缩/98M 压缩后，SM5 库合计约 19.5M 未压缩。

- **方案 A（推荐）：只留 SM5，运行 DX11**。前提：本阶段渲染特性全关（Nanite/Lumen HWRT/PathTracing 本来就要 SM6）。在阶段二后的 ucas（约 131M）基础上预计降到 15~25M。改法：`[/Script/WindowsTargetPlatform.WindowsTargetSettings]` 段删除项目现有两行覆盖 `-D3D12TargetedShaderFormats=PCD3D_SM5` 与 `+D3D12TargetedShaderFormats=PCD3D_SM6`（回落到引擎默认 `+D3D12TargetedShaderFormats=PCD3D_SM5`）、保留 `+D3D11TargetedShaderFormats=PCD3D_SM5`；`DefaultGraphicsRHI` 必须**显式写 `DefaultGraphicsRHI_DX11`**——不能"改回默认"，默认值运行时按 fallback 顺序取首位即 D3D12 跑 SM5（`WindowsDynamicRHI.cpp`），并非 DX11。
- **方案 B：只留 SM6**（DX12）。若未来要保 SM6 特性，则删除 `+D3D11TargetedShaderFormats=PCD3D_SM5` 行，省约 8~13M（压缩后估算），代价是失去 DX11 回退（老核显/9 系显卡跑不动）。
- 补充：`bShareMaterialShaderCode` 在 5.8 已默认开启（收益已在手）；`bSharedMaterialNativeLibraries` 对 Windows 无收益不开；`bConsolidateStaticMeshVertexColors` 在 5.8 已不存在，勿配。Linux/Mac 的 TargetedRHIs 段不进 Windows 包（源码核实），可整段删除防误打包。

## 六、阶段四：压缩固化与零散项

1. **压缩配置持久化**（当前压缩参数只在命令行，ini 里没有，有回归风险）写入 `DefaultGame.ini`：
   ```ini
   [/Script/UnrealEd.ProjectPackagingSettings]
   bCompressed=True
   PackageCompressionFormat=Oodle
   PackageCompressionMethod=Kraken
   PackageCompressionLevel_TestShipping=7
   PackageAdditionalCompressionOptions=-compressionblocksize=256KB
   bPackageCompressionEnableDDC=True
   ```
   注意压缩级别按构建类型分键（`CopyBuildToStagingDirectory.Automation.cs`）：UAT 非 `-distribution` 的 Shipping 构建读 `PackageCompressionLevel_TestShipping`，不是 `_Distribution`；引擎默认 `_TestShipping=4` 正是现状 Kraken L4 的来源，写 `_Distribution=7` 对当前链路**不生效**。
   可选：`PackageCompressionMethod=Leviathan`（社区实测比 Kraken 再省约 5~7%；官方注释其解压略慢于 Kraken，打包时间增加。阶段二/三后压缩基数仅几十 M，实际再省约 1~3M）。注意：shader 字节码熵高（实测仅 2.15:1），压缩对 ucas 的进一步收益有限，主杠杆仍是阶段三。
2. **删 `d3d12SDKLayers.dll`**（4.7M，D3D12 调试层）：微软官方明确"不应装在终端用户机器"，发布版本本就不启用调试层。注意删除自带的匹配版本**并不能**消除 PATH 误加载旧版本的崩溃隐患——引擎注释（`AgilitySDK.Build.cs`）所述风险是 PATH 中存在错版 SDKLayers 会被盲目加载，与是否自带无关。**`D3D12Core.dll`（4.6M，Agility SDK 运行时）在默认 D3D12 RHI 下必须保留**；若阶段三方案 A 强制 DX11-only，两个 DLL 均不再被加载（但引擎无条件暂存，安装版无法从配置阻止），可一并删除再省 4.6M。
3. **NVaftermath（5.5M）决策**：项目已设 `r.GPUCrashDebugging=False`，但该主开关为 0 时会回落到个体特性 CVar，而 `r.GPUCrashDebugging.Aftermath` 默认为 1（`RHICoreNvidiaAftermath.cpp`）——Aftermath 实际仍初始化并加载 DLL（本机 `Pet/Saved/Logs/Pet.log` 实证：`r.GPUCrashDebugging:0` 生效后即出现 `Aftermath initialized`），GPU 崩溃转储当前是活的。要彻底禁用需另设 `r.GPUCrashDebugging.Aftermath=0` 或命令行 `-nogpucrashdebugging`。删除 DLL 本身不影响运行（缺失时仅告警并静默跳过初始化），代价是失去用户机器 GPU 崩溃转储；与阶段一"Shipping 无日志"叠加后，渲染进程 GPU 崩溃类问题将无诊断手段。建议：首发版本删，若后续需要 GPU 崩溃分析再留。
4. ucas 与 pak 并存是正常架构（uasset 类进 ucas，ini/ufont 等松散文件进 pak），无需处理。

## 七、阶段五：桥接程序瘦身（独立于 UE，收益 94M+）

`kimi-petd.exe`/`kimi-pet-bridge.exe` 均为 `bun build --compile` 产物，各内嵌完整 Bun 运行时（98.5M），业务 JS 仅 143KB。

1. **P1（先做）：合并单 exe 双模式**。转发器与守护进程合为一个 exe，按 `process.argv` 分发（`--relay` / `--daemon` / `--daemon-recovery`）；`bridge/packaging/kimi-pet/kimi.plugin.json` 里 12 个 hook 的 command 改为 `.\bin\kimi-petd.exe --relay`。磁盘 188M→94M。需实测 hook command 带参数的宿主行为（MVP 只验证过无参路径）。代码现状有三个改动点：两个入口均为 import 即执行（`bridge/main.ts`、`daemon/main.ts` 末尾 `void main()`），须重构为导出 main + argv 门控的分发入口；`spawnDaemonIfNeeded` 当前以无参方式拉起守护进程，合并后须传 `--daemon`；恢复 worker 经 `process.argv[0]` 自拉起，合并后该路径须保留 `--kimi-pet-recover` 分发。顺手加 `--minify`（收益 <100KB）。
2. **P2（中期）：转发器用 Go 重写**。转发器入口确为"stdin → 命名管道 → exit"，但 `relayHostEvent` 实际包含关闭抑制状态机、恢复交接文件锁（TTL + 所有权）、在途租约与恢复 worker 协议，转发器侧约千行——Go 重写是千行级协议移植而非几行薄客户端，排期按此估。Go 产物 1~3M，relay 单项磁盘从 94M 降到 1~3M（省约 92M）；但与 P1 **不叠加**——守护进程继续用 Bun（94M），无论是否先做 P1，终态磁盘均为 daemon 94M + Go relay ~2M ≈ 96M。P2 的真实收益是冷启动与资源占用：relay 每事件拉起一次，从"加载 94M Bun 运行时"降到毫秒级。守护进程逻辑复杂（约 2600 行），继续用 Bun。
3. **不推荐 UPX 加壳**：杀软误报有公开记录（UPX 官方讨论、ESET），且启动显著变慢（社区实测 44ms→268ms~1.15s，见文末来源；非本机实测），对每事件拉起的转发器是硬伤。
4. pkg 已归档弃用、Node SEA 收益小（仅省 ~29M 且仍 experimental），均不采用。
5. 需补回两个 exe 的脚本化构建（构建脚本已随 `scripts/package.ts` 删除而丢失，现存 exe 是 08-01 旧脚本的最后产物，当前无脚本化重建能力）。

## 八、验证与回归方法（每阶段必做）

统一打包命令（所有阶段共用）：
```bat
"C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun ^
  -project="D:\Workspace\UnrealProject\KimiPet\Pet\Pet.uproject" ^
  -noP4 -platform=Win64 -clientconfig=Shipping -cook -build -stage -pak ^
  -iostore -compressed -nodebuginfo -clean -prereqs
```
（`-prereqs` 随包暂存 `Engine/Extras/Redist/en-us/vc_redist.x64.exe`：根目录 bootstrap exe 的前置检查要求目标机器 VC++ 运行库 ≥ 引擎构建工具集版本（5.8 为 14.50.35719，公开下载渠道最新仅 14.44.x），不满足时运行包内安装器自愈；不暂存则老机器直接弹“缺少 Microsoft Visual C++ 2015-2022 Redistributable (x64)”退出。）

每改一类设置后三件套量化（均本机实测可用）：
1. **目录级**（Git Bash 执行，花括号展开依赖 bash）：`du -sh Pet/Saved/StagedBuilds/Windows/{Engine,Pet}`；
2. **容器级**：`UnrealPak.exe Pet-Windows.ucas -List` 按目录汇总（基线为 08-10 StagedBuilds 构建：ShaderCode 115.2M / Engine 110.9M / Pet 0.6M，与第一节 dist 基线非同一产物，口径一致、构建日期不同）；
3. **文件级存档**：`UnrealPak.exe <Paks目录> -AuditFiles -CSV=build-audit.csv`，两次构建 CSV 直接 diff——注意 **`-AuditFiles` 只审计 .pak，不覆盖 .ucas**，ucas 内容（Shader + 引擎资产，包体最大单项）的文件级对比须用方法 2 的 `-List` 输出 diff 补全；`Manifest_UFSFiles_Win64.txt` / `Manifest_NonUFSFiles_Win64.txt`（带平台后缀）也可直接 diff 看文件增减。

注意：改渲染 ini 后需清 shader 缓存再 cook，否则对比失真；阶段二/三改动后必须全量 cook（`-clean`），不能用 iterate。可选开启 `WriteBackMetadataToAssetRegistry` 后用 `AssetSizeQuery` commandlet 输出按资产的体积 CSV。

## 九、不确定项（明确标注，执行时需留意）

1. 关闭各渲染特性的**精确 MB 级收益**无公开实测数据（官方均为定性声明）；阶段三后 ucas 15~25M 的终值为估算，阶段三完成后以本计划第八节方法产出本项目基准数据。
2. SM5-only 方案下若保留 `r.Substrate` 等 SM6 特性会 cook 报错——方案 A 必须以特性全关为前提。
3. NNEDenoiser 内容体积已实测收敛：源文件 53M，ucas 内条目合计 98.4M（`-List` 口径），本计划按 98M 计。
4. `kimi.plugin.json` hook command 带参数（`--relay`）未实测。
5. Oodle 官方文档的 ini 键名 `PakFileCompressionFormats` 与 5.8 源码实际字段 `PackageCompressionFormat` 不一致，本计划以源码为准，首次打包后从日志 `Using compression format` 行确认生效。
6. `scripts/package.ts` 已丢失，恢复时需与当前 `bridge/src` 结构（daemon 入口 `dist/daemon/main.js` 等）核对。
