# KimiPet 技术文档

本文档介绍 KimiPet 的系统架构、渲染链路、宿主插件、守护进程、通信协议、源码结构和开发方式。玩法与功能介绍见仓库根目录的 [README](../README.md)。

## 系统架构

KimiPet 由三个独立进程组成：

```text
Kimi Code CLI
      │ 每次事件钩子启动一次
      ▼
kimi-pet-bridge.exe             短生命周期转发器
      │ 事件命名管道
      ▼
kimi-petd.exe                   常驻守护进程
      │ 双向控制命名管道
      ▼
Pet.exe                         UE5 渲染进程
      ├─ Win32 逐像素透明宠物窗口
      └─ Slate 与 UMG 会话面板
```

Kimi Code 的事件钩子是短生命周期命令，无法直接承担长期状态管理。转发器因此只负责快速交付事件；守护进程负责跨会话状态、事件恢复和渲染进程生命周期；UE5 进程专注于角色呈现与桌面交互。

## 宿主插件与转发器

插件清单位于 [`bridge/packaging/kimi-pet/kimi.plugin.json`](../bridge/packaging/kimi-pet/kimi.plugin.json)。它监听以下 12 类 Kimi Code 事件：

- 会话：`SessionStart`、`SessionEnd`、`UserPromptSubmit`。
- 工具：`PreToolUse`、`PostToolUse`、`PostToolUseFailure`。
- 执行：`Stop`、`StopFailure`、`Interrupt`。
- 子代理与通知：`SubagentStart`、`SubagentStop`、`Notification`。

每个事件都会拉起一次 `kimi-pet-bridge.exe`。转发器从标准输入读取宿主事件 JSON，将原始文本封装为 `host_event`，提取可用的 `session_id` 后写入事件管道。业务字段由守护进程防御性解析，转发器不依赖宿主事件的完整字段集合。

转发器采用失败放行策略：连接与写入的总超时为 200 毫秒，守护进程未运行时以分离方式拉起，仍未送达的事件暂存到 `%TEMP%\kimi-pet-events\`。无论事件是否成功交付，转发器都以退出码 0 结束，避免阻塞 Kimi Code 主流程。

并发钩子使用锁文件、投递租约和恢复交接机制协调，防止重复启动守护进程，并维持用户关闭与下一次会话恢复之间的事件顺序。

## 守护进程

`kimi-petd.exe` 使用 TypeScript、Node.js 22 和 ESM 实现，运行时只依赖 Node.js 标准库。它不是 Windows 服务，也不注册开机启动，而是在首个合法宿主事件到来时按需运行。

守护进程的主要职责包括：

- 按 `session_id` 维护活跃会话、工作状态、未读状态和任务集合。
- 聚合全局 `Idle` 与 `Working` 状态，并作为宠物状态的唯一权威。
- 将工具调用、子代理和通知事件转换为任务与通知协议消息。
- 以 200 毫秒窗口合并同一会话的高频任务事件。
- 读取 Kimi Code 会话目录，将历史记录与实时会话状态合并。
- 管理 `Pet.exe` 的启动、心跳、断线、退出和指数退避重启。
- 在渲染进程重新连接后补发会话、任务和宠物状态快照。
- 回放转发器暂存的事件，并在退出前持久化宠物窗口位置。
- 响应 `open_tui`，打开指定 Kimi Code 会话或继续最近会话。

全局状态遵循“任一会话忙则 `Working`，全部会话闲则 `Idle`”的规则。忙会话默认 10 分钟没有新事件时强制转为空闲，避免遗漏结束事件后永久卡住；异常会话连续 60 分钟没有事件时才从活跃集合清理。

渲染进程异常退出时，守护进程按照 1、2、4、8 秒的序列退避重启，60 秒窗口内最多尝试 5 次。收到新的宿主事件后可以开启下一轮尝试。

## 渲染进程

渲染进程是 Unreal Engine 5.8 C++ Runtime 工程。角色使用 Skeletal Mesh、Animation Blueprint 和 Control Rig，场景通过独立捕获组件输出到透明桌面窗口。

### 宠物本体渲染链路

```text
UE 场景、灯光与骨骼动画
      ▼
SceneCaptureComponent2D
      ▼
320 × 320 BGRA8 RenderTarget
      ▼
FRHIGPUTextureReadback 异步回读上一帧
      ▼
反转 Alpha，清理全透明像素 RGB
      ▼
UpdateLayeredWindow
      ▼
Windows 桌面
```

`USceneCaptureComponent2D` 使用 `SCS_FinalColorLDR`，目标纹理为 `320 × 320` 的 `PF_B8G8R8A8`。`FRHIGPUTextureReadback` 在渲染线程异步复制上一帧，避免同步 GPU 回读阻塞游戏线程。

Scene Capture 输出采用预乘 RGB 与反向不透明度 Alpha。CPU 侧执行 `A = 255 - A`，并把完全透明像素的 RGB 清零，再交给 `UpdateLayeredWindow`。这一处理保证数据满足分层窗口的预乘 Alpha 语义，同时消除色调映射抖动对透明背景的颜色污染。

宠物窗口使用以下 Win32 扩展样式：

- `WS_EX_LAYERED`：逐像素透明合成。
- `WS_EX_TOPMOST`：保持在普通应用窗口上方。
- `WS_EX_TOOLWINDOW`：不显示为普通任务栏窗口。
- `WS_EX_NOACTIVATE`：交互时不主动抢走前台焦点。

窗口命中测试读取当前帧的 Alpha。不透明像素返回 `HTCLIENT` 并接收点击、拖拽与摄像机操作；透明像素返回 `HTTRANSPARENT`，输入继续传给桌面下方窗口。

透明渲染链路的取证、Alpha 语义和性能验证见 [技术验证报告](技术验证报告-方案一.md)。

### 默认窗口隐藏

守护进程使用以下参数启动渲染进程：

```text
-NOSPLASH -windowed -ResX=16 -ResY=16
```

项目模块通过 Slate `OnPreTick` 守卫，在默认游戏窗口首次绘制前将其隐藏。渲染进程不使用 `RenderOffScreen`，因为会话面板需要创建真实的平台窗口。

### 会话面板

会话面板不经过 GPU 回读链路，而是由 `Notification` 类型的 Slate Popup `SWindow` 直接承载 UMG 内容：

- `FPetSessionWindowHost` 管理窗口生命周期、显隐、左右锚定、工作区约束和窗口级动画。
- `UPetSessionPanelWidget` 管理会话快照、增量更新、空状态和 `UListView`。
- `UPetSessionRowWidget` 管理单行的活跃、工作、未读和点击状态。

窗口使用 `ActivationPolicy::Never`，自动显示时不主动激活应用。面板会根据宠物所在显示器的可用空间选择左侧或右侧，并在 Slate 屏幕坐标与物理像素之间处理 DPI 转换。

详细的职责边界与窗口方案见 [Slate 与 UMG 会话面板方案](Slate与UMG会话面板方案.md)。

## 进程间通信

KimiPet 在同一 Windows 用户会话中使用两条命名管道：

```text
\\.\pipe\KimiPet.H2D.<用户名>   转发器 → 守护进程
\\.\pipe\KimiPet.PET.<用户名>   守护进程 ↔ 渲染进程
```

协议使用 UTF-8 JSON 文本流，每个紧凑 JSON 对象以换行结尾，单条消息上限为 64 KB。消息信封结构为：

```json
{
  "v": 1,
  "type": "pet_state",
  "id": "消息编号",
  "ts": "时间戳",
  "session_id": null,
  "payload": {}
}
```

当前协议主版本为 1。未知消息类型会被忽略并记录；非法信封返回 `protocol_error`，但不会中断后续消息。控制管道连接建立后，双方首先交换 `hello` 与能力列表。

协议消息包括：

- 宿主与会话：`host_event`、`session_start`、`session_end`、`session_state`、`sessions_snapshot`。
- 宠物与任务：`pet_state`、`task_start`、`task_end`、`tasks_snapshot`、`notify`。
- 渲染回传：`open_tui`、`heartbeat`、`pet_moved`、`close_pet`。
- 生命周期与诊断：`hello`、`shutdown`、`protocol_error`。

UE 控制客户端通过 `FRunnable` 工作线程和 Win32 重叠 I/O 收发管道数据，再把完整消息交给游戏线程解析。渲染进程每 3 秒发送一次心跳，守护进程默认 10 秒没有收到合法消息时判定连接失联。断线期间 UE 保持最后一个权威状态，不自行推导新的 `Idle` 或 `Working`。

完整消息字段、事件映射与关键时序见 [MVP 设计](MVP设计.md)。

## 终端与会话目录

点击会话行后，渲染进程发送 `open_tui`，由守护进程负责打开目标。默认打开目标 `open_target=cli` 时启动终端：

```text
wt.exe -d <工作目录> cmd /k kimi --session <会话编号>
```

没有指定会话编号时使用 `kimi --continue`。Windows 终端不可用时，守护进程回退到 `cmd.exe /c start`。

`open_target=web` 时，守护进程改为用系统默认浏览器打开 `open_web_url` 模板 URL（支持 `{session_id}` 占位符）。官方文档确认 `kimi web` 在本地提供 web UI（默认端口 58627），但未公开「直接按会话 id 打开指定 CLI 会话」的 URL 格式；因此默认仅指向本地 web 首页，按会话恢复的 URL 属未验证假设，可用 `open_web_url` 自行配置。当 `open_web_url` 为回环地址（`127.0.0.1`/`localhost`/`::1`）时，守护进程打开浏览器前先确保 kimi web 服务可用：TCP 探测 `host:port` 已在监听则直接开浏览器；未监听则以可见终端窗口拉起 `kimi web --no-open --port <端口>`（按 `terminal` 配置优先 Windows Terminal（`wt`），`wt` 不可用时回退传统 cmd 窗口）并轮询等待端口就绪（最多约 10 秒）后再开；该终端窗口即服务生命周期，用户关闭窗口即停止 kimi web 服务，下次点击会话时探测不到端口会自动重新拉起。拉起失败或超时记错误日志并按既有逻辑向渲染进程补发失败气泡。kimi web 的 web UI 默认要求 bearer token，官方机制是 URL 的 `#token=` 片段自动认证：守护进程打开浏览器前仅对回环地址 URL 读取 token 文件 `%KIMI_CODE_HOME%\server.token`（未设 `KIMI_CODE_HOME` 时回退 `~/.kimi-code/server.token`），读到非空 token 即给 URL 拼上 `#token=<token>` 免密进入，文件缺失或不可读则静默回退裸 URL（用户可从拉起服务的终端窗口横幅复制 token 手动填入）；非回环 URL 一律不拼 token，防止泄漏到远端。非回环 URL 不做自动拉起，直接打开浏览器（无法代管远端服务）。

会话目录来自 `%KIMI_CODE_HOME%\session_index.jsonl` 以及各会话目录下的 `state.json`。守护进程过滤非法或归档记录、按更新时间去重排序，并与实时活跃状态合并，最多向渲染进程发送 50 条记录。

## 数据与配置

守护进程读取 `%KIMI_CODE_HOME%\kimipet\config.json`。未设置 `KIMI_CODE_HOME` 时，路径回退到 `%USERPROFILE%\.kimi-code\kimipet\config.json`。字段缺失或类型非法时逐项使用默认值。

```json
{
  "renderer_path": "D:\\Apps\\KimiPet\\renderer\\Pet.exe",
  "heartbeat_interval_ms": 3000,
  "heartbeat_timeout_ms": 10000,
  "restart_max_attempts": 5,
  "restart_window_s": 60,
  "host_grace_seconds": 120,
  "auto_quit_with_host": true,
  "terminal": "wt",
  "open_target": "cli",
  "open_web_url": "http://127.0.0.1:58627/",
  "session": {
    "staleMinutes": 10,
    "cleanupMinutes": 60
  },
  "log_level": "info"
}
```

运行时文件位置如下：

| 内容 | 路径 |
|---|---|
| 守护进程日志 | `%KIMI_CODE_HOME%\kimipet\logs\kimi-petd.log` |
| 宠物窗口状态 | `%APPDATA%\KimiPet\pet-state.json` |
| 事件暂存 | `%TEMP%\kimi-pet-events\` |
| 用户关闭标记 | `%TEMP%\kimi-pet\pet.disabled` |

这些文件可能包含工作目录、会话信息或命令摘要。提交问题或测试样本前应先检查并脱敏。

|---|---|
| 宿主集成 | Kimi Code CLI 插件、事件钩子、标准输入 JSON |

## 构建与测试

### Bridge

```powershell
cd bridge
npm ci
npm run build
npm test
```

`npm run build` 将转发器、守护进程和协议编译到 `bridge/dist/`。`npm test` 使用 Node.js 内置测试运行器，覆盖协议校验、状态机、事件暂存与恢复、渲染进程监管、终端唤起和 Windows 命名管道集成。

### UE 工程

使用 Unreal Engine 5.8 打开 `Pet/Pet.uproject` 并编译 `PetEditor`，也可以从已配置的开发者 PowerShell 中执行：

```powershell
& "C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\Build.bat" PetEditor Win64 Development "D:\path\to\KimiPet\Pet\Pet.uproject" -WaitMutex
```

只调试渲染进程时，可以先运行模拟守护进程：

```powershell
node --experimental-strip-types tools/mock-daemon.ts
```

模拟守护进程会下发会话数据，并定时交替发送 `Idle` 与 `Working`，便于独立检查面板、状态切换和断线重连。

自动化验证入口包括：

- `bridge/test/`：Node.js 单元测试与 Windows 命名管道集成测试。
- `Pet/Source/Pet/Private/**/Tests/`：状态、输入和会话面板的 UE Automation Test。
- `tools/verify-pet-operations.ps1`：编辑器或打包版本的 Windows 窗口行为验证。

## 插件目录

可安装插件的目录结构为：

```text
kimi-pet/
├─ kimi.plugin.json         # Windows 宿主清单（command 直启 bin/kimi-petd.exe）
├─ kimi.plugin.wsl.json     # WSL 宿主清单（command 走 bin/kimi-pet-relay.sh）
├─ deploy.sh                # 跨平台部署脚本（WSL/macOS/Linux 入口；Windows 经 Git Bash 提示用 deploy.ps1）
├─ deploy.ps1               # 跨平台部署脚本（Windows 原生入口）
├─ bin/
│  ├─ kimi-petd.exe
│  └─ kimi-pet-relay.sh     # WSL 内经 interop 启动 kimi-petd.exe 的 POSIX sh 包装
└─ renderer/
   └─ Pet.exe 及 UE 打包依赖
```

部署时先在插件根目录运行随包的部署脚本，脚本会自动识别当前平台、就位对应平台清单（并备份/恢复 `kimi.plugin.json`）后打印安装指引：

```text
Windows:  powershell -NoProfile -ExecutionPolicy Bypass -File deploy.ps1
WSL:      sh deploy.sh        # 或 ./deploy.sh
```

然后在 Kimi Code 中安装包含 `kimi.plugin.json` 的目录：

```text
/plugins install D:\Apps\kimi-pet
/reload
```

插件会随第一条合法会话事件按需启动后台组件，无需手动运行三个可执行文件。

WSL 宿主（Kimi Code CLI 运行在 WSL、守护进程仍在 Windows）安装时，`deploy.sh` 会把随包分发的 `kimi.plugin.wsl.json` 覆盖为插件根下的 `kimi.plugin.json`（原 Windows 版备份为 `kimi.plugin.json.bak`），并自愈 `bin/kimi-pet-relay.sh` 的执行位（zip 解压会丢 POSIX 权限位）：其 hook 命令走 `bin/kimi-pet-relay.sh`，经 WSL interop 直启 Windows 侧的 `bin/kimi-petd.exe`。同一插件目录回到 Windows 使用时，`deploy.ps1` 检测到 WSL 版清单会从备份恢复 Windows 版。

## 平台边界

完整项目面向 Windows 11。宠物本体、控制通信和命名管道包含 Windows 专用实现；会话面板虽然使用 Slate 与 UMG，但完整程序不具备其他平台的运行基线。

命名管道使用进程默认安全描述符，协议本身没有额外认证令牌。部署环境应把 KimiPet 视为同一用户会话内的本地应用，不应将管道暴露为跨用户或远程接口。
